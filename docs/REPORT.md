# Hearthwatch — Technical Report
## OpenCV AI Competition 2026, Agentic Vision path

## 1. Problem
A household camera records, but nobody watches the recording. Three
common household situations go unnoticed until they become emergencies
or losses: a person falls and cannot call for help; a stove burner is
left glowing; a package sits at the door uncollected. Existing camera
products either record passively or send a notification for every
motion event, which households learn to ignore. Hearthwatch closes the
gap with an agent: it perceives the scene, decides what matters, acts
at the right urgency, and then verifies its own alerts against fresh
vision.

## 2. Users and beneficiaries
- Older adults living alone or with family nearby, and the family
  members who worry about them.
- Any household with a stove, a door, and a camera — no new hardware
  is required beyond a camera that can feed frames to the pipeline.
- The system is designed for one household camera, not for
  multi-camera surveillance: it stores no video by default and keeps
  only event records (time, zone, kind, score, state).

## 3. Architecture
See `architecture.svg` (generated by `docs/make_diagram.py`).
The pipeline is three stages plus a store:

1. **Perception (`src/sentinel.py`, OpenCV 5.0.0).** Each frame
   passes through MOG2 background subtraction (motion), contour
   analysis (shape and size), HSV-independent colour logic for stove
   glow (bright red-dominant pixels in the stove zone), and
   nearest-centroid tracking with a 30-frame aspect history.
   A frozen reference frame (captured after the 30-frame warm-up)
   supplies static-object detection: things that differ from the
   empty room but are not moving.
2. **Agent loop (`src/agent.py`).** Detections become events with
   tiers: `log` (presence), `notify` (left object, stove glow),
   `escalate` (fall-like). Two verification behaviours make this
   agentic rather than reactive: a stove alert resolves itself when
   fresh frames show the glow gone, and household false-alarm
   feedback nudges thresholds (bounded at 2x, so feedback can quiet
   but never silence the system).
3. **Demo server (`src/app.py`, Python standard library only).**
   A single-page UI lists test scenes, runs the pipeline, shows an
   annotated video with detection boxes, lists events, and offers
   acknowledge / false-alarm buttons that act on real agent state.
4. **Deployment.** The code is containerised (`Dockerfile`, pinned
   `requirements.txt`). The AWS deployment is specified in
   `aws-deploy/ECS-DEPLOY.md` (ECS Fargate + Application Load
   Balancer, same container) but has NOT been executed, for the
   reason stated in section 6.

## 4. OpenCV 5 implementation
- **Version:** opencv-python 5.0.0.93, numpy 2.5.4 (pinned).
- **Motion:** `createBackgroundSubtractorMOG2` (history 200,
  varThreshold 25, shadows off), followed by morphological close and
  open with a 5x5 kernel, then `findContours` with external
  retrieval. Blobs under 1200 px are ignored as noise.
- **Tracking:** nearest-centroid matching within 120 px, 10-frame
  miss tolerance, 30-frame aspect history. A fall-like event fires
  when a track's aspect drops from ≥1.2 (standing) to ≤0.7
  (low/wide) within 5 frames.
- **Stove glow:** red-dominant bright pixels
  (R>150, R>G+40, R>B+60) inside the stove zone (default:
  bottom-right quarter, overridable). An alert needs 5 consecutive
  glow frames above a 2% zone fraction.
- **Left object:** static-reference difference, short blobs only
  (height <100 px, so a pausing person is not a package), still for
  30 frames, excluding the stove zone (glow cross-talk) and boxes
  already explained by a fall event (fallen-body cross-talk).
- **Deliberately classical:** no neural model is used. The pipeline
  runs on any CPU, is fully explainable, and its failure modes are
  measurable — which is why the evaluation below can be trusted.

## 5. Evaluation
Method: six synthetic scenes generated with OpenCV itself
(`src/make_testset.py`), each with a frame-labelled ground-truth
manifest (`evaluation/testset/manifest.json`). Scored mechanically
by `src/evaluate.py`. All scenes start with 35 empty frames so the
reference frame shows the empty room.

| Scene | Expected | Result | First seen | Latency |
|---|---|---|---|---|
| walk | presence | HIT | frame 45 | 10 frames |
| fall | fall_like | HIT | frame 124 | 4 frames |
| package | left_object | HIT | frame 135 | -10 frames* |
| stove | stove_glow | HIT | frame 80 | 5 frames |
| empty | none | PASS, no false positives | — | — |
| lighting | none | PASS, no false positives | — | — |

Recall on event scenes: 1.00. False positives: 0.
Unit tests: 8/8 pass (`tests/test_hearthwatch.py`).

\* The package window in the manifest starts when the box is fully
alone (frame 145); the detector fired at frame 135 because the box
had already sat still for 30+ frames. Early detection of a genuinely
static object is correct behaviour, not an error.

## 6. AWS deployment — and the gap, stated plainly
The competition requires a meaningful component on AWS. A standard
AWS account requires a credit card on file. This project's operator
does not put a card on file anywhere, so no AWS account was created
and the AWS deployment has not been executed. The code is
container-ready and the deployment is fully specified
(`aws-deploy/ECS-DEPLOY.md`). The one card-free route — an AWS
Educate Starter Account (no credit card, capped credits, limited
services, managed by a third party) — requires the entrant to apply
with a student email and await approval, a human step with an unknown
timeline. If that account lands before the deadline, the same
container deploys to ECS unchanged. Until then, the live demo runs
on a free host, and this report says so instead of implying
otherwise.

## 7. Limitations and failure cases
- **Synthetic evaluation.** The numbers above describe staged scenes
  with rectangles and ellipses, not real homes. Real rooms add
  occlusion, pets, curtains, mirrors, and changing daylight. The
  pipeline's behaviour on those is unmeasured and must not be
  overstated.
- **Presence is a heuristic.** "Person-like presence" means a tall,
  persistent, moving contour. It will miss a seated person and may
  fire on a tall moving object (a door, a large dog on hind legs).
  It is not a person detector and must not be described as one.
- **Fall-like is a candidate signal.** A collapse can also be
  someone lying down deliberately, dropping a tall object, or a
  camera knock. The escalation exists so a human checks — it is not
  a diagnosis and the system never calls emergency services.
- **Lighting.** A global brightness change is handled (MOG2 adapts;
  the lighting scene passes), but a fast strobing light or a
  camera auto-exposure hunt was not tested.
- **Single camera, fixed zones.** The stove zone is configured per
  deployment; a moved camera or moved stove needs reconfiguration.
- **No video storage.** By design, annotated video exists only for
  demo runs. A household wanting recordings would need to add
  storage with its own privacy review.

## 8. Responsible use
- **No facial recognition.** People are labelled "person-like
  presence" from shape and motion only. No identity, no templates,
  no biometric storage, ever.
- **No autonomous emergency calls.** Escalation means an urgent
  alert to the household, which stays open until acknowledged. The
  system never contacts emergency services, and the film and report
  both state this.
- **No surveillance creep.** One household camera, event records
  only, no video retention by default. The tool is for the
  household's own safety, not for watching other people.
- **Honest numbers.** Every performance figure in this report and
  the film comes from the evaluation run above and is reproducible
  with the commands in the README. Nothing is benchmarked on data
  the system never saw.

## 9. Reproduce it
See README.md: install pinned dependencies, generate the test set,
run evaluation (expect 4/4, 0 false positives), run unit tests
(expect 8/8), start the demo server and run any scene.
